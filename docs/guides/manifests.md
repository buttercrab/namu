# Manifests

NAMU supports two sources of truth:
- `namu.toml` for project-level configuration (preferred).
- JSON manifests inside task artifacts and workflow bundles (generated by the CLI).

## Project config (`namu.toml`)
`namu build` will read `namu.toml` when present and generate the task and workflow bundles under `dist/`.

Example:
```toml
[project]
name = "my-pipeline"
workflows_crate = "examples/distributed/workflows"
registry = "namu"

[registry.namu]
index = "https://registry.namu.dev/index"

[tasks.analyze]
crate = "analyze"
version = "0.1.0"
path = "examples/distributed/tasks/analyze"
kind = "single"
runtime = "wasm"
trust = "trusted"
resource_class = "cpu.small"

[workflows]
export = "auto"

[workflows.doc_stats]
version = "0.1.0"
```

Use `namu sync` to update `Cargo.toml` dependencies and `.cargo/config.toml` registries.

## Task manifest (`manifest.json`)
When building from task directories directly, each task directory contains a `manifest.json`
matching `namu_proto::TaskManifest`. With `namu.toml`, `namu build` generates it.

Minimal example:
```json
{
  "task_id": "analyze",
  "version": "0.1.0",
  "task_kind": "single",
  "runtime": "wasm"
}
```

`runtime` is `wasm` (a WASM component, runs anywhere) or `native` (a shared library, runs only on
the platform it was built for). Set `"checkpoint": true` for tasks with external side effects:
their branch is logged past them before it continues, so crash recovery never runs them again.
`"retries": N` tries a call that fails again, up to N more times, under the same call key:
first after `"retry_backoff_ms"` (default 100), then twice as long each time, up to 30 s. Only
the task's own failures are retried (an error it returns, a trap, a Python process that dies);
once they run out, the last one fails the branch. A task that fails with a type of its own is
retried only for the variants `"retry_on"` names (as serde names them, `["rate_limited"]`); any
other error value is its answer.
For a stream task, `"window"` limits how many of its items are in flight at once (default 1024).
For a batch task, `"batch_size"` is how many items a session holds at once (default 32),
`"max_wait_ms"` makes an idle session wait for a full batch (unset: it steps at once), and
`"batch_slots"` is how many sessions each worker runs (default 1). `namu build` fills in `checksum` (sha256 of the binary) and, for
native tasks, `platform`. The orchestrator rejects artifacts whose binary does not match the
checksum, and treats versions as immutable: republishing the same version with a different
artifact is refused.

`namu build` also records the task's `signature`: what a call of it takes and gives, in the IR's
types. A Rust task says it itself: its types derive `namu_guest::Describe`, and `namu build`
reads the signature from a build of the crate for the machine it runs on (for a WASM task, that
is a second build). A Python task's is read from its annotations, by parsing the module without
running it (see [Tasks](tasks.md#signatures)). It is not written by hand. A task that fails with a
type of its own records it as the signature's `error` (see [Tasks](tasks.md#errors)).

When a workflow is published, every call in it is checked against the signature of the task
version it pins, so a workflow that gives a task the wrong types is refused then, with where and
why, rather than failing its runs:

```text
workflow doc_stats@0.1.0 does not fit its tasks:
call to `analyze` (op 4): argument 2: field `min_len`: `String` is read as `u64`
```

A task built without a signature (an artifact built elsewhere, or by an older `namu`) is not
checked; `namu publish` names the tasks whose calls were not.

## Workflow upload payload
`namu build` copies workflow IR JSON files into `dist/workflows/`. `namu publish` uploads them as:

```json
{
  "id": "etl_pipeline",
  "version": "0.1.0",
  "ir": { "operations": [] },
  "task_versions": { "add": "0.1.0" }
}
```

Workflow files must be named `*.workflow.json`.
